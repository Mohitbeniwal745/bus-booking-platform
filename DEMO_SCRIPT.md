# 3–5 Minute Demo Video Script & Walkthrough Guide

Follow this exact timestamped guide to record your 3–5 minute demo video. Reviewers specifically grade you on showing:
1. CI/CD pipeline run.
2. Clean deployed service & Swagger UI.
3. Health/Readiness & structured JSON logs.
4. Concurrency test passing (Acceptance criteria).
5. Failure & self-healing recovery drill.
6. Backup & restore script execution.

---

## ⏱️ Video Timeline (Target: ~4 Minutes)

### [00:00 – 00:45] Intro & CI/CD Pipeline
* **What to say**:  
  *"Hello, my name is [Your Name], candidate for the DevOps & Cloud Engineering assessment on the Bus Booking Platform. Today I will demonstrate our production-grade containerized service, automated CI/CD pipeline, concurrency protection, observability, and disaster recovery."*
* **What to show on screen**:  
  * Open GitHub in browser: Show the GitHub Actions tab.
  * Show the 4 pipeline stages green: **Lint (Ruff)**, **Unit Tests (Pytest)**, **Security Scan (Trivy)**, and **Docker Build & Tag**.
  * Highlight the commit SHA tag generated by the pipeline.

---

### [00:45 – 01:30] Architecture & Running Containers
* **What to say**:  
  *"The application is containerized with a secure multi-stage Dockerfile running as a non-root user. Let's look at our running Docker Compose stack."*
* **What to show on screen**:  
  * Terminal: Run `docker compose ps`.
  * Point out that all three containers (`bus_booking_nginx`, `bus_booking_app`, `bus_booking_db`) are running and **`(healthy)`**.
  * Browser: Open `http://localhost:8000/docs` (or `https://localhost/docs`).
  * Show the interactive OpenAPI endpoints: `/trips`, `/trips/{id}/seats`, `/bookings`, `/health`, and `/ready`.

---

### [01:30 – 02:15] Concurrency Safe Booking (Acceptance Test #1)
* **What to say**:  
  *"One of the core acceptance criteria is that concurrent requests for the exact same seat cannot produce duplicate bookings or duplicate PNRs. We solved this using atomic database row-level locking. Let's run the automated concurrency test."*
* **What to show on screen**:  
  * Terminal: Run `python scripts/test_concurrency.py`
  * Explain the output:  
    *"As you can see, 4 simultaneous requests were fired. Exactly 1 request succeeded with HTTP 201 and received PNR [point to PNR], while the remaining 3 were rejected safely with HTTP 409 Conflict."*

---

### [02:15 – 03:00] Observability & Structured JSON Logs
* **What to say**:  
  *"For observability, the application outputs standardized structured JSON logs with correlation IDs, response latencies, and HTTP status codes. We also separate liveness from readiness."*
* **What to show on screen**:  
  * Terminal: Run `curl http://localhost:8000/health` (Liveness 200 OK).
  * Run `curl http://localhost:8000/ready` (Readiness 200 OK, database connected).
  * Run `docker compose logs --tail=10 app` to show clean JSON log format.

---

### [03:00 – 03:45] Failure Injection & Self-Healing Drill
* **What to say**:  
  *"Now let's demonstrate failure diagnosis and self-healing. I will intentionally kill the database container."*
* **What to show on screen**:  
  * Run `docker compose stop db`.
  * Run `curl -i http://localhost:8000/ready` $\rightarrow$ Show the **HTTP 503 Service Unavailable** error.
  * Run `docker compose start db`.
  * Wait 3 seconds and run `curl -i http://localhost:8000/ready` $\rightarrow$ Show it automatically recover back to **HTTP 200 OK**.

---

### [03:45 – 04:30] Backup & Restore Drill & Conclusion
* **What to say**:  
  *"Finally, let's verify our disaster recovery runbook by taking a hot snapshot of the database and executing a restoration."*
* **What to show on screen**:  
  * Terminal: Run `.\scripts\backup.ps1` (or `bash scripts/backup.sh`). Show the new `.sql` snapshot created in `./backups/`.
  * Run `.\scripts\restore.ps1` (or `bash scripts/restore.sh`). Show the database restore complete successfully.
* **Closing Statement**:  
  *"All steps, runbooks, and rollback procedures are fully documented in our repository README and RUNBOOK. Thank you."*
